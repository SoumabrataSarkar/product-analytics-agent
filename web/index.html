1. The data model and its logic

A data model is the blueprint for the information: what a user, session, view or transaction represents, which columns each record has, and how records connect. It describes what is valid; it does not itself create data.

The generator expresses conditions as Python code. A loop creates records; conditions keep them consistent. An episode view is associated with a user, session and episode. A refund refers to an original payment, and its positive value is subtracted when calculating net revenue.

“Rules” are code: loops, conditions, calculations, fixed inputs and random selections—not a separate set of natural-language instructions that Python reads.

Some choices define a synthetic business story, including activity targets. Others describe valid journeys and relationships. The data model and checks document the intended constraints.

2. Why SQLite?

SQLite is a database engine that stores tables, indexes and records in one portable file. Python can create it using its built-in sqlite3 library; a separate database server is not necessary.

It suits a local, reproducible dataset: a reviewer can create or open one file and query it with SQL. It is not an enterprise warehouse, and its concurrency and deployment trade-offs differ from server-based databases.

The reviewed database is local. The repository contains the generator and checks, not the generated SQLite file. Editing the generator does not automatically change a previously generated file.

3. What is the generator?

generate.py is a Python program. It opens a new SQLite file, creates tables, builds fictional records and inserts them. It uses Python’s standard library, including random and sqlite3; it does not call an AI model to write every row.

The program combines fixed inputs, repeated loops and conditional logic with random selections. It creates cohorts of users, selects eligible users for monthly activity, and constructs associated sessions, views, payments and subscription history. IDs and timestamps connect the records.

Targets + seed → create tables and fictional entities → create linked activity and payment records → save SQLite file → run separate checks.

4. Numbers, randomness and the seed

Some values are explicitly set in code: the generator creates 24,000 users, with fixed signup-cohort sizes, and uses monthly active-user and subscription-payment targets. It selects which eligible users contribute to those totals using a seeded random generator.

Other details—such as selected users, sources or timestamps—vary through random choices. Many choices combined produce different fictional journeys. Conditions restrict choices where the data needs to remain coherent.

The seed 8126 starts a repeatable pseudo-random sequence; it does not contain the data itself. Keep the same generator version, seed and compatible environment to reproduce the dataset. A changed program can produce different results with the same seed.

The roughly 20% increase in average monthly active users between the two three-month periods is a designed target, not an independently discovered real-world trend.
python3 examples/pockettoons/generate.py --output pockettoons.sqlite
python3 examples/pockettoons/check_data.py pockettoons.sqlite

Run from the project folder with Python 3. Use a new output name: the generator refuses to overwrite an existing file. Record the Git commit and environment for reproducibility.

5. How the tables connect

Each table describes a different kind of thing at its own level of detail, or grain. A user can have many sessions; a session can contain many views; an episode can appear in many views. A user can have payments and subscription periods across different sessions.

User → sessions → content views → episode → series
User → transactions → content attribution → episode
User → subscription history
User events connect actions to relevant sessions, views or payments.

IDs are the join keys. Timestamps let an analysis ask what was true when an event happened, rather than applying a user’s current status to an old view. Session links may be absent for off-session transactions such as renewals.

Joining multiple one-to-many tables directly can duplicate amounts or views. Aggregate each fact to the required grain before combining it, and check counts and revenue after joins.

6. Why Bronze, Silver and Gold?

The three layers separate different jobs, not three physical database servers. The design uses one SQLite file with logically distinct tables.

Bronze · preserve

Keep source records close to how they arrived, including errors, so discrepancies can be traced and audited.

Silver · prepare

Validate and standardize detail, retain lineage and document exceptions. Use this level for detailed investigation.

Gold · summarize

Build selected, reconciled metrics at known grains for common questions. Use only where requested dimensions and definitions are supported.

One flattened table mixes raw values, corrections and aggregates, making it harder to audit changes and easier to duplicate facts. Separate layers introduce extra transformations and maintenance, but make responsibilities clearer.

The current fixture contains raw payment evidence and curated transaction values, but the complete prefixed, transformed and reconciled Bronze/Silver/Gold implementation is still planned.

7. What is an implanted data issue?

It is a deliberate imperfection in fictional source data used to test whether an analysis notices problems and handles them appropriately. It is not an error observed in real customer data.

1

Missing acquisition source

Some users’ sources are unknown. Overall totals can still be computed, but channel-level analysis should quantify and disclose the unknown group rather than assign it to a channel.

2

Raw payment values

Some amounts are stored as text, unavailable, or 100 times the intended amount. An exaggerated amount can distort revenue if summed without checking.

3

Review and correction evidence

raw_payment_source retains raw amounts; payment_quality_review records reviewed corrections; transactions holds the corrected amount. A calculation using the curated amount is not proof that an agent detected the raw problem independently.

Generation checks test selected integrity and quality conditions; passing them is not a guarantee that every possible analytical issue has been ruled out.

How the agent would work through a question

Example: “Why did active users increase while revenue stayed flat?” These steps describe the intended workflow, not results from a running agent.

1

Understand the question

Identify the metric, comparison period and population. If “revenue” or the comparison window is ambiguous enough to change the answer, ask a clarifying question. The planned metric registry supplies definitions once implemented.

2

Validate the baseline and data

Calculate the movement using selected definitions. Check coverage, time windows, unknown acquisition sources, payment anomalies and freshness. A weak baseline means the agent must qualify or stop the analysis.

3

Form evidence-led hypotheses

Explore possible explanations, such as a change in acquisition mix or conversion. The design allows up to three distinct hypotheses per round; these are questions to test, not conclusions.

4

Choose a safe query and layer

Use the catalog to understand table grain and joins. A suitable Gold aggregate may answer a broad trend; Silver detail can examine user cohorts; Bronze can trace a questionable raw payment. The planned query tool is read-only and bounded.

5

Inspect evidence and iterate

Record SQL, results and caveats; mark each hypothesis supported, rejected, inconclusive or not tested. Continue for at most three automatic rounds, stopping earlier if evidence is sufficient or limits require it.

6

Explain what is known—and what is not

Report quantified findings, evidence, uncertainty and next steps. If material questions remain, show partial results and invite the user’s direction. An association in synthetic data is not proof of causation.

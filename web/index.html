The agent

Your Codex or Claude Code environment does the reasoning. This repository supplies its investigation method, definitions and Python tools.

The data

PocketToons is a fictional streaming product. One SQLite file contains the source data and Bronze, Silver and Gold layers for April–September 2026.

The evidence

Each material query has a log. Reports state definitions, periods and limits. Eighteen scenarios were evaluated; one remains partial.

See the evaluation →

Get started

You need Git, Python 3.9+, SQLite 3.37+ through Python, and your own working Codex or Claude Code environment.

  1. Clone the repository

    If it is private, sign in to an account with repository access first.

    git clone https://github.com/SoumabrataSarkar/product-analytics-agent.git
cd product-analytics-agent
python3 -c "import sys, sqlite3; print('Python:', sys.version); print('SQLite:', sqlite3.sqlite_version)"

  2. Download the database

    Get pockettoons.sqlite from the database folder ↗. Save the completed download locally outside the repository, for example in ~/pockettoons-data/. It is approximately 680 MiB and already includes all three layers.

    Use this reviewed file as supplied. No generation or layer-building step is needed.

    Verify the download

    On macOS run shasum -a 256 ~/pockettoons-data/pockettoons.sqlite; on Linux use sha256sum. Substitute your actual path.

    Expected SHA-256:

    8d39e78bbaa756b594c9e38797490dc1879f2980a05f966aaf62d3919517790b

    If it differs, ask the project owner which snapshot was shared before proceeding.

  3. Open the repository in your coding agent

    Open the cloned folder in Codex or Claude Code. Start a fresh chat there and paste the prompt below. Replace the two absolute paths; the example question is ready to run.

Your first prompt

Use this repository to investigate a PocketToons product question.

Database: /absolute/path/to/pockettoons.sqlite
I authorize you to read and query this file. Do not modify, regenerate, or overwrite it. If you cannot access it, ask me instead of choosing another database.

Read AGENTS.md and follow the shared product analytics investigation skill. Read the architecture, data catalog, metric registry, and layer contracts. Check the database build status and available Bronze, Silver, and Gold objects; record the snapshot and versions. Use the repository's read-only query and evidence tools for material checks. Ask me if missing information could change the answer; do not invent definitions.

Work independently: do not read docs/evaluations/, evaluation-results/, submission/, previous investigation reports, answer keys, the generator's answer-bearing README, or question-specific investigation guides.

Question: How did monthly active users change from April through September 2026 across all identified users? Use the approved MAU definition and explain any coverage limits.

Output folder: /absolute/path/to/a/new/investigation-folder
Save a Markdown report and the evidence logs there. Record the start and end times, query count, and repository commit or download date. If the folder already exists, use a new folder rather than overwriting an earlier run.

Replace the database and output paths before sending.

The agent may ask a focused follow-up, then saves a Markdown report and query evidence in your chosen output folder. Text reports and queries need no extra Python packages.

Want a PDF report?

From the repository root, create a virtual environment and install the optional report packages, then ask for a PDF in your prompt:

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

The PDF renderer limits reports to ten pages. See the full setup guide ↗ for tests and optional dataset regeneration.

01 / Investigation architecture

Question → evidence → answer

Follow the sequence to see what each step does and which project files support it.

Definitions, layer contracts and evidence guide each investigation.

Investigation pathHover over a step

  1. Start with the business question

    Identify what the person wants to understand: the metric, comparison period, population and decision. If a missing detail could change the answer, ask a focused follow-up before proceeding.

    Unclear request → ask → return to the question.

    Guided byArchitecture v1 · investigation policy ↗

  2. Read definitions and understand the data

    The metric registry defines the measure, population and approved calculation. The data catalog explains what each table contains, its grain, safe joins and known gaps. If a definition is not approved or does not fit the request, clarify or label a suitable ad hoc variant.

    Consult these filesMetric Registry ↗Reference Data Catalog ↗Reference Data Model ↗

  3. Check trust, then establish the baseline

    Check the relevant time coverage, missing values, source quality and compatible joins. Calculate the requested measure for comparable periods. A material data issue may require a qualified answer or a pause, rather than a confident explanation.

    Check and contextFixture validation checks ↗Data-quality issue log ↗

  4. Choose the most useful investigation path

    Break down the baseline, then prioritize checks that can distinguish credible explanations. Explore users, revenue, content or source quality as relevant—not every branch for every question. Up to three hypotheses per round and three automatic rounds are allowed; stop earlier when justified.

    New evidence → refine the next check or revisit an assumption.

    Design referenceInvestigation & evaluation paths ↗Scenario guides describe expected checks. Keep them out of independent investigation sessions.

  5. Query the right detail and record evidence

    The read-only query tool runs bounded SQL and logs each query as evidence. The registry, catalog and layer contracts decide the source: Gold answers supported monthly questions from reconciled tables; Silver holds validated detail such as user-days, payments and episodes; Bronze views expose the unchanged source for audits.

    Consult these filesLayer contracts ↗Gold question list ↗Query and evidence tools ↗

  6. Explain the answer and what remains unknown

    Present quantified findings, definitions, source and time window, evidence, limitations and a recommended next step. If credible checks are exhausted or a quality problem blocks confidence, share the partial result and invite human direction. Association alone is not causation.

Why the choice matters

If a summary lacks the required grain or is stale, the agent should use the appropriate detail instead.

In the PocketToons database, build_layers.py builds 20 Bronze views, 10 Silver tables and 8 monthly Gold tables in one transaction and reconciles them with 122 checks; the source tables are never changed. Correctness, coverage and freshness take priority over speed.

01 / Evaluation workflow

From a scenario to a scored, improved agent

Seven steps, from defining the questions to publishing the results.

The scored runs and evidence are available in the repository.

  1. Define the scenarios

    Eighteen questions cover simple aggregates, filtered queries, comparisons, cohorts, multi-step investigations, data-quality traps, an ambiguous request that should get a clarifying question and an unanswerable one that should get a clear decline. The scenario file describes routes and success criteria. Keep it out of independent investigation sessions.

    Defined inInvestigation paths & scenarios ↗

  2. Prepare independent source references

    For scenarios with numbers, the evaluator records the expected values, the traps a good answer must report and the behaviour that fails. Values come from the metric registry’s SQL run read-only on the source tables only, never on the Silver or Gold tables the agent uses, so the key does not simply repeat the agent’s pipeline. The reference batches were reviewed in small topic groups; Q02 used reviewer source checks, and Q03’s clarified weekly values were checked after its run. The published copies must be excluded from independent agent sessions.

    Record when each reference was prepared and disclose exceptions.

    MethodMetric Registry ↗Evaluation process ↗

  3. Run the agent blind

    A fresh session in Claude Code or Codex receives only the question, the database path and “independent mode”. It follows the shared skill, logs every read-only query as evidence and, when a report is requested, builds the fixed-template PDF (at most 10 pages).

    A session that has seen the answer key or the scenario guide is not independent.

    Agent usesShared investigation skill ↗Query, evidence and report tools ↗

  4. Score against the key

    The evaluator compares the run with the answer key: Pass, Partial, Fail or Not run. Numbers must match within fixed tolerances, and behaviour counts too: claiming a cause from an association, mislabelling a comparison period or skipping a material data-quality caveat fails even when the numbers are right.

    Recorded withEvaluation run template ↗

  5. Review and keep the raw output

    A reviewer checks the report against its evidence and the source data. The original agent output is kept unchanged. A corrected version can be prepared for the deliverable, but it is assessed separately and never turns a failed run into a pass.

    Deliverable formatInvestigation report template ↗

  6. Improve the agent and rerun

    Each failure type becomes a rule in the shared skill or a guard in a tool, such as the report generator’s 10-page limit. Failed scenarios are rerun in new sessions to confirm the fix.

    Failure → rule or guard → rerun.

    Changes go toShared investigation skill ↗Report generator ↗

  7. Publish the results

    After the blind runs, expected-versus-actual results, the failure analysis and the write-up are added to the repository so reviewers can check them.

    TemplatesOne-page write-up template ↗

03 / Rules that keep it fair

Independent references

Expected answers are prepared independently. Q02 used reviewer source checks; Q03’s clarified weekly values were computed after its run. The key is never changed to match an agent; a genuine mistake is corrected openly and logged.

Independent method

The key is computed from the source tables with the registry’s SQL, not from the Silver and Gold tables the agent queries.

Fresh, blind sessions

Each run starts in a new session with only the question. A session that has seen the key or the scenario guide cannot produce an independent result.

Behaviour counts

Correct numbers are not enough. Overstated certainty, mislabelled comparisons or a missing data-quality caveat fail a run.

Where things live: scenarios, the skill, tools and this process are in the repository. The published results, answer key and run records are for reviewers. Keep them out of future independent investigation sessions. Read the evaluation process ↗

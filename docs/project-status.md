## Scope and current file placement

- **Common project:** This file, [Architecture v1](architecture/v1.md), the architecture decision records and the [layer build workflow](data-layers/layer-build-workflow.md) describe project-wide status, the intended framework or a dataset-independent method. An ADR is an Architecture Decision Record: a document explaining an important design choice and its trade-offs.
- **PocketToons-specific:** The [reference data model](examples/pockettoons-reference-data-model-v1.md), [data catalog](examples/pockettoons-data-catalog.md), [metric registry](metrics/metric-registry.md), [layer contracts](data-layers/pockettoons-layer-contracts.md), [Gold question list](data-layers/pockettoons-gold-questions.md) and `examples/pockettoons/` code describe or use this example's data and business decisions. They are shared across agent runtimes; their SQL and approved definitions must not be assumed valid for a different product.
- **Current placement:** These links reflect the repository as it exists. The metric registry lives under `docs/metrics/` and the layer contracts under `docs/data-layers/` even though their current content uses the PocketToons fixture. A future per-project organization can make that distinction more explicit. No folder migration or new paths are decided here.
- **Authority:** The catalog and reference model govern their documented dataset; approved metric definitions are in the registry; layer tables follow their contracts. A different dataset needs its own reviewed definitions, mappings, contracts, limitations and source contracts.

## Completed and accepted for this stage

1. **Architecture v1:** Frozen design and ADRs define an LLM-neutral, evidence-led analytics workflow, bounded investigation and logical Bronze/Silver/Gold layers. The architecture is a design baseline, not a running agent.
2. **Reference data model:** The PocketToons example provides a detailed relational model, business rules, temporal relationships and safeguards. It is a reference fixture for a generalized analytics framework, not a claim that the agent is specific to one product.
3. **Synthetic data:** A deterministic Python generator, SQLite fixture and validation suite (186 checks) cover users, sessions, content, subscriptions, payments, refunds, events, attribution and intentional data-quality issues. The data includes logged-out browsing, uncaptured funnel links, about 60% engaged active users, a visit at every signup, uneven platform and country mixes and PPV refunds at about 3%, while monthly MAU and net revenue stay at their targets. The [issue log](examples/pockettoons-data-generation-issue-log.md) records generation issues, analytical impact and resolution or limits.
4. **Data catalog:** All 20 fixture tables have catalog entries. Soumabrata Sarkar personally read and reviewed the catalog in depth, identified gaps, requested and approved changes, and accepted the earlier reviewed tables without repeating the review. This is acceptance for the current stage, not a claim of complete production coverage or machine-readable agent integration.
5. **Metric registry:** Every metric in the metric map is approved: MAU v1.1, the activity family, stickiness and engagement rate, growth accounting, the revenue group v1.1, the funnel and lifecycle group, the engagement group and the supporting metrics v1.1, plus a table of requests the data does not support. Canonical SQL runs on SQLite 3.37 or later and is exercised by isolated tests and the fixture checker.
6. **Data layers:** The [layer build workflow](data-layers/layer-build-workflow.md) records the method, contract format, safety rules and known blockers. `examples/pockettoons/build_layers.py` builds 20 Bronze views, 10 Silver tables and 8 monthly Gold tables in one transaction inside the database file, after checking the source schema; it records the source fingerprint, definition versions and all 122 reconciliation results in `layer_build_log`, and a failed check rolls the build back. Every table's contract is in the [layer contracts](data-layers/pockettoons-layer-contracts.md); Gold follows the approved [question list](data-layers/pockettoons-gold-questions.md). `silver_quality_exceptions` lists the 13 reviewed raw payment corrections; curated tables are clean by design.
7. **Event, payment, marketing and identity safeguards:** Event timestamps and properties, episode links, paywall/checkout links, refund and subscription links, raw-payment coverage and units, review timestamps, marketing day/channel comparison and identity lifetime have documented checks and targeted tests.
8. **Query and evidence foundations:** Bounded read-only SQLite queries, per-query evidence logs and the shared investigation skill exist with targeted tests. `tools/report_pdf.py` renders the investigation report as a PDF with one fixed template and refuses reports over 10 pages; the skill requires it when a report is requested and for the assignment deliverable.
9. **Static visual explorer:** `web/index.html` is a documentation prototype, not a connected AI frontend or working agent.

The reviewed local database contains the current source with Bronze, Silver and Gold (build `3a0dbed21d2f45958aefa2887a0cadd8`, 2026-11-09): all 186 source checks and 122 layer checks passed and the source fingerprint was unchanged by the build. ### Future idea: project-specific knowledge-base updater

This is an idea for later discussion, not an implemented or approved architecture change. When connecting another data source, a future updater could inspect the available schema and ask the user about business definitions, joins, time rules, exceptions and data-quality expectations. It could then propose a project-specific catalog, metric registry, layer contracts and mappings for the user to review and approve.

Definitions from one project should not silently overwrite or become assumptions for another. Generated changes would need validation, versioning and user approval, with access and sensitive-data safeguards. The updater's architecture and the eventual folder structure remain to be designed.

The order of dependent work may be refined with the user; do not represent planned components as implemented.

## Data location and reproduction

The reviewed SQLite file is a local artifact, not a committed GitHub file. A fresh database can be created, checked and layered from repository code:

```sh
python3 examples/pockettoons/generate.py --output pockettoons.sqlite
python3 examples/pockettoons/check_data.py pockettoons.sqlite
python3 examples/pockettoons/build_layers.py pockettoons.sqlite
```

The generator **creates a new database file** at the path supplied after `--output`; if no path is supplied, it uses `pockettoons.sqlite` in the current working directory. It refuses to run when that file already exists so an existing database, including manual changes, is not silently overwritten. The source is about 0.56 GB, or about 0.71 GB with the layers.

The checker reads the specific file path passed to it and exits non-zero when any check fails; check the exit status, not only the printed lines. The builder writes layer tables into the file it is given; build on a local disk, because SQLite writes through some shared or network folders can fail, then copy the finished file. Changing generator or builder code changes what a **future** run produces; it does not update a database file that already exists. Record the generator and builder versions, seeds and any separate changes for the exact fixture being analyzed.

The main seed is 8126; marketing uses an independent seed, 10844. The generator also uses other independent streams for specific behaviour, so a change to one behaviour does not shift unrelated values. Seeds make the generator's random selections repeatable for the same generator version and compatible environment; they do not contain the database. Review completion times are NULL when unknown.

## Instructions for the next collaborator

- Read `AGENTS.md`, `CLAUDE.md`, the frozen `docs/architecture/v1.md`, relevant ADRs, the catalog, the reference data model, the metric registry and the layer contracts.
- Work on the evaluation with the user: propose the answer key one scenario group at a time, keep it out of the agent's investigation context, and confirm material choices before locking them in. Explain problems and recommendations in short, simple language.
- Keep shared analytical definitions model-neutral. Do not implement separate Claude-only metric logic, silently invent metric semantics, or reopen accepted catalog tables, registry definitions or layer contracts without a concrete issue.
- Distinguish implemented, tested code from proposed behaviour; do not claim the agent is evaluated or working end to end until it is.
- Change layers through `build_layers.py` and their contracts, and rebuild; never edit layer tables by hand. Check the checker's and builder's results, not only that they ran.
- Do not edit frozen Architecture v1. Any architecture change requires the documented ADR/version process.
- Write contracts as direct final descriptions. Reserve issue/impact/resolution history for the issue log; do not add unsolicited interview coaching.
- Avoid assumptions of causation, silent quality corrections, cross-session identity claims or fact-join fanout. Preserve raw values and distinguish unknown review times from known historical availability.
- Keep the repository private and avoid committing confidential assignment materials, secrets or API keys.
